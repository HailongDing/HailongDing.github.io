A Disk That Looks Full But Isn’t: Understanding Btrfs Space

Categories: filesystems  storage  troubleshooting 

A customer asked a reasonable question: a disk (/dev/vdd) that had no data on it was reporting a large amount of used space. Where was it going?

The disk was a Btrfs filesystem, mounted under a Docker data directory. The answer involved two separate things stacked on top of each other — how Btrfs accounts for space, and an actual filesystem error underneath — and untangling them is a good tour of why "used space" on a modern filesystem is not a single simple number.

The starting picture

The disk was reporting significant usage. Inspecting it showed a Btrfs filesystem mounted at the container runtime's data root, and the standard tools pointed at the directories consuming the most space. So far, so ordinary — except the customer was adamant the volume held little actual data, and the numbers did not match that.

The first thing to understand is that on Btrfs, df is not the whole truth. Btrfs manages space in a two-level scheme that df flattens and, in some situations, reports misleadingly. You need the filesystem's own accounting tools to see what is really going on.

How Btrfs allocates space

Btrfs does not hand raw blocks straight to files. It works in two stages:

  • It carves the device into large chunks (block groups), each dedicated to a type: data, metadata, or system.
  • Files are then written into the data chunks; the filesystem's own bookkeeping lives in the metadata chunks.

Crucially, metadata is redundant by default. On a single device Btrfs uses the DUP profile for metadata — it keeps two copies of all metadata, so a localised corruption of one copy can be repaired from the other. That redundancy costs space, and it is space that holds no user data at all. This is by design and is one of Btrfs's resilience features, but it means "used" includes duplicated bookkeeping that a naive reading would not expect.

To see the real breakdown you use Btrfs's own commands rather than df:

# chunk-level allocation: how much is data vs metadata (note DUP), and used vs total
$ sudo btrfs filesystem usage /mnt/point

# per-type summary
$ sudo btrfs filesystem df /mnt/point

These distinguish two very different quantities that df conflates: space allocated to chunks, versus space actually used within those chunks. A chunk that has been allocated for data but is mostly empty still counts as "allocated," which can make the disk look fuller than the live data justifies.

The Docker layer: reclaimable images

Because this Btrfs volume backed a container runtime, a chunk of the "usage" was reclaimable container data — old image layers, stopped containers, build cache. The container runtime reported how much of that was reclaimable:

$ docker system df          # shows RECLAIMABLE per category
$ docker system prune -a    # reclaim unused images, networks, build cache

Reclaiming it freed real space — but not as much as expected. After the prune, a substantial amount of space was still reported as used. This is where the two explanations separate: some of the "used" space was reclaimable container junk (now gone), but some of it was not being released even though it should have been.

The part that didn't add up

Even after pruning containers and asking Btrfs to reclaim, the available space stubbornly plateaued — it would not climb past a certain figure, no matter what we freed. On a healthy filesystem, deleting data and reclaiming chunks should return that space to the free pool. It wasn't happening.

Two more tools come into play here:

# reclaim partially-used data chunks by rewriting them fuller (balance)
$ sudo btrfs balance start -dusage=50 /mnt/point

A balance consolidates partially-filled chunks — it rewrites the live data from mostly-empty data chunks into fewer, fuller ones and returns the emptied chunks to the free pool. This is the normal cure for "Btrfs says it's full but the data doesn't justify it," which happens when data ends up spread thinly across many allocated-but-underused chunks. It helped somewhat, but the space still capped out below what the accounting said should be free.

Then a simple experiment settled it: we rebooted the machine, and afterwards the available space jumped up. A plain reboot recovering space is not normal Btrfs behaviour — a well filesystem does not need a restart to release space it has already been told to free. That reboot-fixes-it signature pointed at filesystem state that had gotten stuck, not merely at allocation accounting.

The actual fault: a filesystem error

On investigation, the filesystem did indeed have an error. So the customer's problem was really two problems wearing one symptom:

  1. Expected Btrfs behaviour — duplicated metadata and allocated-but-underused chunks made the disk look fuller than the live data implied. This is normal and is addressed with prune + balance.
  2. An actual filesystem error — which was preventing space from being released properly and only cleared on reboot. This is not normal and is the real defect.

The lesson is not to stop at the first plausible explanation. "Btrfs over-reports usage" is true and would have been a satisfying-sounding answer — but it only accounted for part of the numbers. The residual, and the tell-tale reboot recovery, revealed a genuine fault sitting underneath the expected accounting quirk.

Checking and fixing

# look for reported errors on each device (per-device error counters)
$ sudo btrfs device stats /mnt/point

# scrub verifies checksums of all data and metadata, repairing from the DUP copy where possible
$ sudo btrfs scrub start /mnt/point
$ sudo btrfs scrub status /mnt/point

# offline structural check (unmount first; --repair is a last resort, snapshot beforehand)
$ sudo btrfs check /dev/vdd

A scrub reads everything and verifies checksums, repairing bad metadata from its duplicate copy — which is exactly what the DUP profile exists for. Persistent structural problems may need an offline btrfs check, and if that reaches the point of --repair, snapshot the volume first — repair operations can make things worse.

The cloud angle

One practical recommendation came out of this. On a cloud platform, prefer cloud block storage for this kind of workload: it can be expanded online when you are genuinely short of space, and it supports snapshots, so you can capture a known-good state before risky operations like a filesystem repair — and roll back if a repair goes wrong. Whatever filesystem you run on top, having cheap snapshots underneath turns "attempt a risky repair and hope" into "snapshot, attempt, roll back if needed."

Takeaways

  • On Btrfs, df lies by omission. Use btrfs filesystem usage / df to separate allocated chunks from used space, and remember metadata is duplicated (DUP) by default.
  • "Full but shouldn't be" is often underused chunks. A balance consolidates them and returns space to the free pool.
  • Container runtimes hoard reclaimable data. Old image layers and build cache count as used until pruned.
  • Don't stop at the first explanation. Expected Btrfs accounting explained part of it; a real filesystem error — betrayed by space only returning after a reboot — explained the rest.
  • Snapshot before you repair. Cloud block storage with snapshots makes risky filesystem operations reversible.
