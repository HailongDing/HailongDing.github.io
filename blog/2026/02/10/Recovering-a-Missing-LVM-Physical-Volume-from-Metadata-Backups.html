Recovering a Missing LVM Physical Volume from Metadata Backups

Categories: storage  recovery  linux 

A customer had an LVM setup where one physical volume had stopped being recognised. The disk was there, the partition was there, but LVM no longer saw it as part of the volume group — which meant the logical volume that depended on it would not activate, and the data on it was inaccessible.

The good news, and the reason LVM is forgiving in situations like this, is that LVM keeps backups of its own metadata. A physical volume whose LVM header has been damaged or wiped can very often be rebuilt from those backups, exactly, because the metadata records the precise identity and layout the PV is supposed to have. Here is the full recovery, step by step.

A brief mental model of LVM

Three layers, bottom to top:

  • PV (physical volume) — a disk or partition initialised for LVM. Near its start sits a label and metadata area identifying it by a unique UUID and describing the volume group it belongs to.
  • VG (volume group) — a pool made of one or more PVs.
  • LV (logical volume) — a slice carved out of the VG, which is what you actually put a filesystem on.

When a PV's on-disk label/metadata is lost, LVM can no longer tell that the disk belongs to the VG, so the VG is incomplete and its LVs will not activate. The fix is to write a correct label back — and because LVM archives its metadata under /etc/lvm/backup/ and /etc/lvm/archive/, we know exactly what that label should contain, including the original PV UUID.

Step 0: back up before you touch anything

Every step below writes to disk. Before any of it, preserve the current state so a mistake is recoverable:

# save the VG's metadata backup file
$ cp -a /etc/lvm/backup/datavg /root/datavg.backup.$(date +%F_%H%M%S)

# save the first 16 MiB of the partition — where the LVM header lives
$ dd if=/dev/vdc1 of=/root/vdc1.head.16MiB.$(date +%F_%H%M%S).img bs=1M count=16
$ sync

That image of the first 16 MiB is your undo button: if rebuilding the header goes wrong, you can restore exactly what was there. On a cloud instance, take a volume snapshot as well — it is the cheapest insurance available.

Step 1: deactivate the volume group

$ vgchange -an datavg

Turn the VG off first, so nothing tries to write to it while you are rebuilding a PV header underneath it. Working on a live VG invites corruption.

Step 2: rebuild the missing PV header

This is the heart of the recovery. pvcreate normally initialises a new PV, which would assign a fresh UUID and wipe existing metadata — the last thing you want. The --uuid and --restorefile options change its behaviour entirely: instead of creating something new, it recreates a PV with the exact original UUID and the layout described in the metadata backup.

$ pvcreate \
    --uuid "zXzvsB-poE5-JRoz-nzt6-sAtD-HgOO-wgp6BD" \
    --restorefile /etc/lvm/backup/datavg \
    /dev/vdc1

The UUID comes from the metadata backup file itself (it records the UUID every PV in the VG is supposed to have), so you are restoring the disk's original identity, not inventing one. Confirm the PV is back and correctly associated with the VG:

$ pvs -o pv_name,pv_uuid,vg_name /dev/vdc1

It should now show the PV UUID belonging to datavg.

Step 3: activate the logical volume

With the PV restored, bring up the LV. Using partial activation mode is prudent during recovery — it will activate what it can even if the VG is not yet perfectly whole:

$ lvchange -ay --activationmode partial datavg/home_lv

# confirm the device-mapper node appeared
$ ls -l /dev/mapper/datavg-home_lv

Step 4: repair the filesystem

The disruption very likely left the filesystem needing recovery (a "needs journal recovery" state is typical). Run a check on the now-visible LV:

$ fsck.ext4 -f -y /dev/mapper/datavg-home_lv

On a large volume this takes a while — let it finish; interrupting it can leave the filesystem in a worse state. When it is done, confirm the filesystem looks clean:

$ file -sL /dev/mapper/datavg-home_lv

Step 5: mount and verify read/write

$ mkdir -p /mnt/home
$ mount /dev/mapper/datavg-home_lv /mnt/home
$ df -hT /mnt/home

# prove it is actually writable, then clean up the test
$ touch /mnt/home/.rw_test && rm -f /mnt/home/.rw_test

Mounting to a scratch path and doing an explicit write test confirms the recovery end to end — the data is present and the volume accepts writes.

Step 6: take a fresh metadata backup

$ vgcfgbackup -f /root/datavg.vgcfgbackup.$(date +%F_%H%M%S) datavg

Now that everything is healthy, capture a clean metadata backup so you are starting from a known-good state going forward.

After this, the disk was recognised normally and the data was fully accessible again.

Why this works

The recovery is possible because of a deliberate LVM design choice: every change to a VG is archived automatically, under /etc/lvm/archive/ (previous versions) and /etc/lvm/backup/ (current). Those text files record the complete topology — every PV's UUID, every LV's extent mapping. So even when a PV's on-disk header is gone, the information needed to recreate it exactly is sitting on the root filesystem. pvcreate --uuid --restorefile is the tool built specifically to use it.

The important discipline is that you are restoring identity, not creating it. The whole recovery hinges on giving the PV back its original UUID; a plain pvcreate would assign a new one and destroy the association the VG expects, turning a recoverable situation into data loss. That is also why Step 0 matters so much — if you get the header rebuild wrong, the saved 16 MiB image lets you try again from the original bytes.

A cloud recommendation

LVM's flexibility on physical servers — pooling disks, carving volumes, extending across devices — is genuinely useful. But on a cloud platform, much of what LVM is used for is provided more simply by cloud block storage: volumes expand online without the PV/VG/LV dance, and snapshots give you point-in-time backups and instant rollback. For a lot of cloud workloads, a single expandable cloud volume with scheduled snapshots is easier to operate and easier to recover than a hand-built LVM stack — and it would have made this incident a snapshot restore rather than a manual header rebuild.

Takeaways

  • A missing PV usually isn't lost data. LVM archives its metadata, so a damaged PV header can be rebuilt exactly.
  • pvcreate --uuid --restorefile restores identity. It recreates the PV with its original UUID from the metadata backup — never run a plain pvcreate on a PV you are trying to recover.
  • Back up the header first. A dd of the first 16 MiB (plus a cloud snapshot) makes the rebuild reversible.
  • Deactivate, rebuild, activate partial, fsck, verify, re-backup. Work on a quiet VG and prove read/write at the end.
  • On the cloud, consider block storage instead. Online expansion and snapshots replace much of what LVM is used for, with far easier recovery.
