When CPU Usage Spikes for No Reason: Correctable Memory Errors

Posted on January 24, 2023 ()

Categories: hardware  troubleshooting  linux 

A customer reported that their server's CPU usage had climbed sharply, even though nothing about their workload had changed — same traffic, same code, same request rate. The graphs showed real CPU being consumed, but the application was not doing more work. Where was it going?

The answer was in the system log, and it had nothing to do with the application. The machine was quietly spending its time correcting memory errors.

What the log showed

The system messages contained a steady trickle of corrected-error events from the memory controller — the kind of line that scrolls past unnoticed until you go looking for it:

mce: [Hardware Error]: Machine check events logged
EDAC MC0: 1 CE memory read error on ... (channel:1 slot:0)
EDAC MC0: 1 CE memory read error on ... (channel:1 slot:0)
EDAC MC0: 1 CE memory read error on ... (channel:1 slot:0)

"CE" is a correctable error. The machine was not crashing, and no data was being lost — but each of these events carries a hidden cost that, in aggregate, was showing up as CPU usage. To understand why, it helps to know what actually happens when a bit in memory goes wrong.

ECC, CE, and UCE

Server memory is protected by ECC (error-correcting code). For every 64-bit word the CPU reads from a cache line, the DIMM also stores 8 bits of ECC data. Those extra bits let the memory controller detect and, within limits, repair corruption:

  • A CE (correctable error) is a bit flip that ECC can fix on the fly. The corrected data is returned to the CPU and, ideally, written back to memory. Nothing is lost.
  • A UCE (uncorrectable error) is corruption too severe for ECC to repair. This is the dangerous case — it typically forces the kernel to take action, up to and including a panic to prevent using bad data.

Why does a bit flip in the first place? Each memory cell stores a 0 or 1 as the charge level of a tiny capacitor. Two things can corrupt it:

  • Hard errors — a physical fault in the DIMM. These reproduce reliably and tend to get worse; the module is failing.
  • Soft errors — a transient disturbance: electrical noise, signal integrity on the board, heat, or even a cosmic ray depositing charge in a cell. These are random and hard to reproduce.

Why a "harmless" error costs CPU

The key is that correcting an error is not free — and the cost depends on how the platform is configured to handle it.

When a correctable error occurs, the platform's RAS (reliability, availability, serviceability) features can report it in one of two ways:

  • CMCI (Corrected Machine Check Interrupt) — handled by the operating system. The OS records the event and moves on. This is cheap.
  • SMI (System Management Interrupt) — handled by the firmware (BIOS), in System Management Mode.

SMI is the expensive one, and here is the crucial detail: an SMI stops every core and hands control to firmware. The OS does not schedule it, cannot see it, and cannot interrupt it. The cores simply freeze while the firmware's handler runs — typically 100–300 ms, and on some older BIOS or BMC versions considerably longer if the handler is inefficient or the errors are not converging.

Most server vendors deliberately handle each individual CE via CMCI rather than SMI, precisely to avoid the risk of frequent memory errors triggering constant firmware pauses. But there is usually a threshold: the CPU's internal CE counter increments on every corrected error, and when it crosses a limit — for example, accumulating a couple of thousand events — the platform escalates to an SMI so the firmware can collect the details of the failing DIMM, log it to the BMC and the system event log, and record which module and what error type.

So the "unexplained CPU usage" was really a combination of two things:

  1. The overhead of the OS logging a continuous stream of CMCI events.
  2. Periodic SMI pauses when the error count crossed the escalation threshold — during which the whole machine was stalled in firmware, showing up as lost time and latency jitter that looks, from the outside, like the CPU being busy.

A DIMM producing errors steadily enough — say, one per second — will march toward that threshold and trigger the escalation on a predictable cadence. The application never got slower; the machine was just being interrupted underneath it.

One more source: memory scrubbing

There is a second way CEs appear, worth knowing because it can look alarming without indicating an acute problem. Many platforms run a background patrol scrub — a RAS feature that periodically walks idle memory (often on a 24-hour cycle), reads each location, and rewrites any data ECC had to correct. This proactively cleans up soft errors before the application reads them.

Errors surfaced this way are scrubbing CEs; errors surfaced when the running system reads a location are read CEs. Both point at the same DIMM, but scrubbing CEs mean the location was found by the sweep rather than hit by the workload.

How to diagnose it

If you see CPU or latency anomalies with no matching change in application behaviour, check for memory errors before anything else:

# Corrected/uncorrected error counts, per DIMM, decoded
$ sudo edac-util -v

# Machine-check events collected by the MCE daemon
$ sudo journalctl -u mcelog
$ sudo ras-mc-ctl --summary
$ sudo ras-mc-ctl --errors

# Raw hint in the kernel log
$ dmesg | grep -iE 'mce|EDAC|Hardware Error'

These tell you whether errors are occurring, whether they are correctable or not, and — most usefully — which physical slot is responsible. The BMC / IPMI system event log (ipmitool sel elist) records the same from the firmware side and survives an OS reinstall.

What to do

  • Replace the DIMM. A module producing a steady stream of correctable errors is failing. Correctable today can become uncorrectable tomorrow, and a UCE is a crash rather than a slowdown. Use the slot information from EDAC or the BMC to identify it. On a cloud instance, this means migrating to healthy hardware — raise it with the provider, who can live-migrate the instance off the suspect host.
  • Don't dismiss it because "nothing crashed." Correctable errors are the early-warning system working as designed. The absence of a crash is not the absence of a problem.
  • Check firmware if pauses are severe. If the SMI handling itself is causing long stalls, a BIOS/BMC update may shorten or fix an inefficient handler — but this treats the symptom; the failing DIMM is still the cause.

Takeaways

  • Unexplained CPU or latency with no workload change is often hardware. The cores may be spending time somewhere the OS cannot even account for.
  • ECC corrects errors, but correction has a cost. A high enough error rate escalates to firmware-handled SMIs that freeze every core for hundreds of milliseconds.
  • SMIs are invisible to the OS. They will not appear in normal profiling; you find them by looking at memory-error counters, not CPU flame graphs.
  • A steady stream of correctable errors means a dying DIMM. Replace it before it produces an uncorrectable one.
