A Game Server Crash Traced to an iptables Lock Under Attack

Categories: security  linux  troubleshooting 

A game company's server crashed hard. What made it puzzling was the monitoring: at the moment it went down, none of the usual resource metrics were anywhere near their limits. CPU, memory, network — all comfortably within range. Servers do not normally crash when they have headroom to spare.

Fortunately the machine was configured to capture a crash dump, so instead of guessing, we could open the vmcore and look at exactly what the kernel was doing at the instant it died.

Reading the crash dump

Analysing a kernel crash dump with the crash utility lets you see the state of every task at the moment of the panic — what each one was executing and what it was waiting on. Two findings stood out.

First: the panic occurred while the system was running iptables. The active task in the panic path was an iptables invocation. That is already a clue — iptables is not something a game server should be running constantly. It is a firewall-configuration tool, invoked to add or change rules.

Second: it was stuck on a file lock. The task was blocked on /run/xtables.lock. This is the lock file modern iptables uses to serialise access to the kernel's netfilter tables — only one process may modify the rule set at a time, and the lock is how that is enforced.

A process stuck on xtables.lock means many iptables invocations were contending for it simultaneously. Something was trying to change firewall rules far faster than the system could apply them.

The smoking gun: one IP, 4,370 times

Digging further into the dump, one client IP address appeared 4,370 times in the moments before the crash. That number is the whole story.

The picture that emerged: the server (or a security script layered on top of it) was reacting to abusive traffic by adding a firewall rule per offending connection. Under a flood from a single source hammering the box, that meant thousands of iptables calls piling up, each one trying to grab xtables.lock, each one waiting behind the others. iptables could not parse and apply rules anywhere near fast enough to keep up, the backlog grew without bound, and the contention eventually took the system down.

In other words, the crash was not caused by the raw volume of attack traffic overwhelming the network. It was caused by the response to that traffic — a rule-per-connection reaction that turned a traffic flood into a lock storm inside the kernel. The defence mechanism was the thing that fell over.

Why iptables behaves this way

The classic iptables model is not built for high-frequency, per-connection rule changes:

  • The lock is global. xtables.lock serialises all rule modifications. Two rule changes cannot happen at once, by design.
  • Each change is expensive. Under the hood, the legacy iptables path retrieves the entire rule set from the kernel, modifies it, and writes the whole thing back. Cost grows with the number of rules — so the more rules you have added, the slower each new addition becomes.
  • Rule matching is linear. A packet is tested against rules top to bottom. A chain that has grown to thousands of entries adds latency to every packet, not just to the tool.

Put those together and a rule-per-attacker strategy has quadratic-flavoured pain: as the list grows, both adding rules and evaluating them get slower, right at the moment the system is under the most pressure.

The right way to handle this

Blocking bad traffic is correct; doing it with one iptables rule per source is not. Better tools exist for exactly this shape of problem:

  • ipset. Instead of thousands of rules, keep one rule that matches against an ipset — a hash-based set of addresses. Adding or removing an address is O(1) and does not touch the rule chain at all. This alone eliminates the lock storm.
  • nftables. The modern replacement for iptables supports atomic rule replacement and native sets and maps, avoiding the full get-modify-set cycle of the legacy tool.
  • A dedicated protection layer. For volumetric attacks, filtering at the host is the wrong place entirely — the packets have already cost you to receive them. A managed DDoS-protection or web-application-firewall service scrubs traffic upstream, before it reaches the instance. That was our recommendation to this customer: put attack mitigation in front of the server rather than trying to have the server defend itself.

The general principle: the data plane and the control plane should not fight each other. Reconfiguring the firewall (control plane) on every packet (data plane) couples them together, so a surge in traffic becomes a surge in configuration churn. Keep the reaction cheap — flip a set membership, not a rule set — and the flood stays a network problem instead of becoming a kernel problem.

Takeaways

  • A crash with resources to spare points at contention, not capacity. Look for locks and serialisation, not saturation.
  • A crash dump turns speculation into evidence. Enable kernel crash dumps on important machines; the panic task and its wait state told us in minutes what metrics could not.
  • Don't add one firewall rule per attacker. Legacy iptables serialises on a global lock and rewrites the whole table per change — a flood becomes a lock storm. Use ipset or nftables.
  • Mitigate volumetric attacks upstream. Scrub traffic before it reaches the host; a server defending itself packet-by-packet is already losing.
