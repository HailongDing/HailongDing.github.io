A Kernel Panic During Unmount: Chasing 17 Million Dentries

Posted on July 28, 2023 ()

Categories: linux kernel  filesystems  troubleshooting 

A server running an old 3.10-series kernel panicked with a soft lockup. The crash utility output that had been retained pointed at something very specific: the machine died while the umount command was tearing down a filesystem, and the CPU was stuck in the kernel's directory-entry cleanup code.

This is a good case to write up not because the root cause is exotic — it is not — but because it is a clean example of reasoning under incomplete evidence. The original vmcore and its matching debug symbols were no longer available by the time the analysis was done, so the write-up has to be honest about the line between what is proven and what is merely very likely. That discipline is worth as much as the conclusion.

The panic

The retained crash summary and call trace showed a soft-lockup panic in the umount process (PID 202413) on CPU 3, with a stack that ran straight through the VFS dentry-teardown path:

dentry_lru_del()
  __d_shrink()
    shrink_dcache_for_umount_subtree()
      shrink_dcache_for_umount()
        generic_shutdown_super()
          kill_block_super()

This stack is highly specific. The CPU was not idle, not blocked on disk I/O, not waiting in user space — it was actively executing dentry destruction as part of unmounting a block-backed filesystem. A soft lockup means it stayed in that kernel path, without yielding, long enough for the watchdog to fire and panic the box.

Alongside it, a snapshot of /proc/sys/fs/dentry-state had been captured:

17603707 17252679 45 0 0 0

What a dentry is, and why 17 million is a lot

A dentry (directory entry) is the kernel's in-memory object linking a path component to an inode — the thing that makes repeated path lookups fast. The kernel caches them aggressively and holds onto unused ones on an LRU list for possible reuse, releasing them only when it needs the memory.

Reading the six numbers against the 3.10 struct dentry_stat_t layout:

nr_dentry17,603,707total dentries allocated (active + unused)
nr_unused17,252,679unused, held on the LRU for reuse
age_limit45reclaim age threshold, seconds
want_pages0no pruning request outstanding right now

That is 17.6 million dentries, 98% of them unused — an enormous cache. And here is the mechanism that turns a big cache into a dead machine: on unmount, the kernel must synchronously walk the filesystem's dentry tree and destroy every entry, and in the 3.10 implementation dentry_lru_del() takes a global LRU lock and decrements counters on each removal. A very large tree therefore becomes a very large amount of serialised, lock-heavy work performed in one uninterrupted stretch of kernel time. Long enough, and the soft-lockup watchdog concludes the CPU has hung.

Ruling out the obvious suspect

The natural first guess for anything involving huge memory structures is "the machine ran out of RAM." The evidence says no. The memory summary showed 174 GB free of 278 GB, no swap in use, and only 11% of memory committed. Slab was 25 GB.

This is not a global out-of-memory event — and it actually explains the huge cache rather than contradicting it. With that much free memory, the kernel had little reason to reclaim clean, reusable dentries, so they accumulated unbothered. The want_pages: 0 in the snapshot says the same thing: no pruning was being requested, because nothing was under memory pressure. The cache grew precisely because there was no pressure to trim it.

The dump also showed heavy Kubernetes activity — systemd and kubelet tasks blocked during memory-cgroup teardown, other tasks waiting on inode mutexes under the cgroup hierarchy. This is strong context: high churn of containers means high churn of namespaces, mounts, and path lookups, which is exactly what generates millions of dentries. On a busy container host, negative lookups and short-lived mounts alone can produce staggering dentry counts.

The honest limitation

Here is where the missing vmcore matters, and where a lesser write-up would overclaim.

/proc/sys/fs/dentry-state is a system-wide counter. It proves the node had 17.6 million dentries. It does not prove which filesystem owned them, and specifically it does not prove that the filesystem umount was destroying was the one holding the bulk of them. To close that gap you would need the live kernel memory: inspect the struct super_block passed to generic_shutdown_super(), read its per-superblock unused-dentry count, and break down the dentry slab by cache. Without the dump, those objects cannot be examined.

So the conclusion is stated at graded confidence:

FindingStatus
Soft-lockup panic occurred during umountConfirmed (panic header + trace)
The stuck path was dentry destructionConfirmed (call trace)
The global dentry cache was enormousConfirmed (17.6M / 98% unused)
Global RAM exhaustion caused the panicNot supported (174 GB free)
Large dentry teardown was the triggerProbable, high confidence
The unmounted FS owned those dentriesUnproven — needs the vmcore

Probable root cause: a very large dentry subtree, combined with synchronous unmount cleanup and contention on the global dcache LRU lock in the old 3.10 kernel, kept CPU 3 in kernel context long enough for the watchdog to declare a soft lockup and panic the system.

Fixing it, and being ready next time

Restore diagnostic readiness first. The single biggest problem in this case was that the evidence needed to prove the cause had been lost. Configure kdump to write to durable storage, and — just as important — retain the exact vmlinux, debug symbols, and kernel package for every production kernel build. A dump you cannot match to symbols is a dump you cannot fully read. Test that kdump actually produces a readable dump during a maintenance window, before you need it.

Monitor dentry growth. Collect nr_dentry, nr_unused, and slab figures over time, and alert on rate of change rather than an absolute threshold — a rapid monotonic climb is far more meaningful than a high steady number on a large-memory host. Correlate with pod create/delete rate and mount count.

Reduce mount and namespace churn. Investigate repeated pod teardown, orphaned mounts, and failed cgroup cleanups. Before node maintenance or a bulk unmount, drain the node and let the runtime finish cleaning up, so the unmount path is not competing with active churn.

A temporary mitigation, used carefully. The kernel can reclaim clean, reusable slab objects on demand:

$ sync
$ echo 2 > /proc/sys/vm/drop_caches

This drops reclaimable dentries and inodes. It is a maintenance-window workaround, not a fix, and it should be disabled by default and used only with logging and a baseline-derived threshold. Tuning vm.vfs_cache_pressure upward (say 150–200 for this kind of high-dentry host) makes the kernel reclaim these caches more willingly, but measure metadata latency before and after — it is not a universal setting.

The real fix is the kernel. A custom 3.10 build is far behind the maintained longterm branches. Migrating to a currently supported, vendor-maintained kernel — with a container and Kubernetes stack tested against it — is the corrective action; the mitigations above only buy time. Canary it against representative pod-churn and mount/unmount workloads, and compare unmount latency and dentry behaviour against the old kernel before rolling out.

Takeaways

  • A soft lockup is "stuck in the kernel too long," not necessarily "out of resources." Here the machine had 174 GB free and still panicked.
  • Caches grow when there is no pressure to trim them. Plentiful free memory is exactly why 17 million dentries could accumulate.
  • Container churn manufactures dentries. High pod and mount turnover is a classic source of runaway path-cache growth.
  • Separate confirmed from probable. A system-wide counter proved the population but not its owner; without the vmcore, the last link stays an inference — and saying so is more useful than pretending otherwise.
  • Protect your evidence. Retain vmcore, matching symbols, and logs before rebuilding a node. The best analysis is limited by what was preserved.
