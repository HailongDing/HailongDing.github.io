Why Your UDP Throughput Falls Short of the Nominal Bandwidth

Posted on September 27, 2023 ()

Categories: networking  performance  linux 

A customer's instance was rated for 9 Gbps of network bandwidth, but their UDP application could not get anywhere near it. TCP tests hit the number; UDP fell well short. Was the rating wrong?

The rating was fine. UDP throughput is limited by something the bandwidth figure does not describe: how fast a single CPU core can push packets. After a good deal of testing, three factors turned out to dominate, and understanding why explains a lot about when a network number is achievable and when it is not.

The three factors that matter

  1. CPU clock speed. Higher core frequency means higher achievable UDP throughput — this was the single biggest lever.
  2. Packet size. Large packets (jumbo frames, ~9 KB) are far more efficient than small ones.
  3. CPU pinning. Binding the sender/receiver to a specific core measurably improves performance.

The reason all three point back to the CPU is the fundamental difference between how TCP and UDP move data.

Why UDP is CPU-bound in a way TCP is not

TCP has a lot of machinery working in its favour for bulk throughput. Segmentation offload lets the kernel hand the NIC one large buffer and have the hardware chop it into packets; generic receive offload coalesces incoming packets before the stack sees them. The effect is that the expensive per-packet work is amortised, and much of it happens in the NIC rather than on a core.

UDP has none of that in the general case. It is a datagram protocol with no reassembly and no offload help — every datagram is processed individually by the CPU, through the full send or receive path: system call, socket layer, UDP layer, IP layer, and out to the driver. That cost is paid per packet regardless of how big the packet is.

So the throughput ceiling is set by packets per second a core can process, multiplied by bytes per packet. That single equation explains all three factors:

  • Faster core → more packets per second. The per-packet cost is largely fixed work; a higher clock does more of it per unit time.
  • Bigger packets → more bytes per packet. Same packet rate, more payload each, so more throughput for the same CPU effort. This is why jumbo frames matter so much for UDP.
  • Pinning → no migration overhead. Keep the flow on one core and you keep its cache warm and avoid cross-core scheduling costs.

The numbers from testing

On a 2.5 GHz instance, 10 Gbps of UDP was simply unreachable — around 5.9 Gbps was the practical ceiling for a single core, no matter what else we tuned. That is the key finding: for a 2.5 GHz core, ~6 Gbps is roughly the wall.

Moving to a 3.2 GHz instance (Intel Ice Lake generation) changed the picture. Testing with iperf3 and jumbo-sized datagrams:

# server
$ iperf3 -s

# client — 8972-byte payload, 5 minutes, UDP, unlimited rate, pinned to core 4
$ iperf3 -c <server-ip> -l 8972 -t 300 -u -b0 -A 4

The flags worth knowing:

  • -l 8972 — payload size. 9000-byte jumbo frame minus 28 bytes of IPv4 + UDP header = 8972 bytes, so the datagram fits in one jumbo frame without fragmentation.
  • -u — UDP; -b0 — no sending-rate cap; -A 4 — pin to core 4 (pick an idle one).

On an 8-core / 16 GB instance of this generation (9 Gbps rating), the unlimited test reached about 12 Gbps but with packet loss — it was overrunning the rating. Capping the send rate at the rating removed the loss:

$ iperf3 -c <server-ip> -l 8972 -t 300 -u -b 9G -A 4

Scaling up to a larger instance (18 Gbps rating) reached about 15.5 Gbps with a little loss unlimited, and ran clean when capped. The takeaway for this CPU generation: the smaller instance was already enough to saturate its 9 Gbps rating from a single UDP flow — the ideal, cost-effective pick for that workload.

How to tune a UDP application

  • Pick a high-clock instance. For UDP-heavy workloads this is the most important choice — it sets the single-core packet-rate ceiling before you tune anything.
  • Send large packets. Push datagram size up toward the jumbo limit, but do not exceed what the network path allows (here, 8972 bytes of payload). Fragmentation undoes the benefit.
  • Pin your threads: taskset -c <core> ./your_program. Keep the hot flow on a fixed core.
  • Watch per-core utilisation, not aggregate. Run mpstat -P ALL 3 on both ends during the test. A single UDP flow pegs one core while the box looks idle overall — the average hides the bottleneck completely. Keep that core below ~90%; once it saturates, loss climbs sharply.
  • Scale out across cores. One flow is capped by one core. To use the full NIC bandwidth, spread traffic across multiple flows/cores (multiple sockets, SO_REUSEPORT, receive-side scaling) so no single core is the limit.

Takeaways

  • A bandwidth rating is a ceiling, not a promise a single flow can reach it. Whether you hit it depends on the CPU, the protocol, and the packet size.
  • UDP throughput is single-core-bound. No segmentation/receive offload means the CPU touches every datagram; packets-per-second × bytes-per-packet is your real limit.
  • Clock speed and packet size are the two big levers. A 2.5 GHz core caps out around 6 Gbps; a 3.2 GHz core with jumbo frames saturates 9 Gbps easily.
  • Measure per-core. Aggregate CPU graphs will tell you the machine is idle while one core is the bottleneck.
