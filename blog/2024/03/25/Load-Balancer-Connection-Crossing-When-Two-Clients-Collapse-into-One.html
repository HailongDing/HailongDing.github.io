Load-Balancer “Connection Crossing”: When Two Clients Collapse into One

Categories: networking  load balancing  cloud 

Two servers started experiencing communication problems at the same moment. Nothing obvious tied them together at first — until we traced the topology and found that each connected out through a load balancer, and both load balancers sat in front of the same pool of backend servers.

That shared backend is the setup for a subtle and genuinely confusing failure mode. The cloud provider calls it "connection crossing" (串流). It has nothing to do with media streaming. It is what happens when two logically separate connections end up looking identical to a backend server, so the backend can no longer tell them apart. This post explains the mechanism, when it happens, and how to avoid it.

How a cloud load balancer forwards traffic

A managed cloud load balancer presents a virtual IP (VIP) and listening port to the outside world, and forwards to a pool of backend servers (real servers, "RS"). It comes in two flavours:

  • Layer 4 forwards based on transport-layer connection information only — protocol plus the address four-tuple. It is typically handled by a high-performance forwarding gateway. It does not look at HTTP host, URL, or cookies.
  • Layer 7 understands the application protocol (HTTP/HTTPS/gRPC) and can route by domain, URL path, header, or cookie. It runs on a proxy tier (commonly Nginx-based) behind the L4 gateway.

A connection is identified by its four-tuple:

source IP : source port  →  destination IP : destination port

Now the crucial detail. Many L4 configurations, and L7 short-connection configurations, use source-IP pass-through (source IP transparency), so the backend sees the client's real IP rather than the load balancer's. That is usually what you want — the backend gets accurate client addresses without needing X-Forwarded-For. But watch what happens to the four-tuple as a packet crosses the load balancer:

client_ip:client_port → vip:vport → rs_ip:rs_port

With source-IP pass-through, the backend ultimately sees only:

client_ip:client_port → rs_ip:rs_port

The VIP and listening port — the very things that distinguished which entry point the client used — have disappeared from the four-tuple the backend sees. That erasure is the seed of the whole problem.

What "connection crossing" actually is

Connection crossing is when two originally distinct front-end connections, after forwarding, converge into the same four-tuple on a single backend server. The backend OS keys its connection table on the four-tuple, so two different logical connections that map to one four-tuple become indistinguishable — packets from one can be delivered to the other, connections reset unexpectedly, data appears corrupted or mixed.

The five conditions — all must hold

Crossing only occurs when every one of these is true at once. That is good news: break any single one and the problem cannot happen.

  1. The client source IP is passed through to the backend (L4, or L7 short-connection with pass-through).
  2. There are multiple distinct front-end paths — two load balancers, two listeners on one LB, or an LB path coexisting with a direct-connect path.
  3. Those paths converge on the same backend IP and port.
  4. The client reuses the same source IP and source port. A client can legitimately reuse a local source port when the destinations (VIP/port) differ — from its point of view the connections are distinct.
  5. The connections overlap in time. Both must be alive simultaneously to collide in the backend's table.

Our incident matched exactly: two load balancers (condition 2), same backend pool (condition 3), source-IP pass-through (condition 1). Here is the collision in concrete terms:

Client establishes, at the same time:
  10.0.0.10:50000 → LB-A:80
  10.0.0.10:50000 → LB-B:80        (same local port, different VIP — legal)

Both LBs forward to the same backend:
  → 172.16.1.20:8080

Backend sees both connections as:
  10.0.0.10:50000 → 172.16.1.20:8080     ← identical. Collision.

To the client these are two different connections to two different VIPs. To the backend they are one four-tuple, used twice.

Does session persistence fix it?

No — and this trips people up. Session persistence (sticky sessions) ensures a given client keeps landing on the same backend. If anything that makes crossing more likely, because it increases the chance both paths pin to the same RS. Persistence solves a different problem (session affinity); it does not add any information to the four-tuple, so it cannot help the backend distinguish two connections that already look identical.

Layer 4 vs Layer 7 risk

The risk is much higher at L4. Pure L4 forwarding passes the client four-tuple straight through, so it satisfies condition 1 by default.

L7 gives you a natural escape. In backend long-connection mode, the L7 proxy connects to the backend using its own source IP and a port it allocates — the real client IP travels in the X-Forwarded-For header instead of the four-tuple:

LB backend-IP : LB-allocated-port → rs_ip:rs_port

Because the proxy's own address now occupies the source fields, two different clients no longer produce the same backend four-tuple. Condition 1 is broken, and crossing cannot occur. You get the real client IP from the header rather than from the connection.

How to avoid it

Break any one condition:

  • Don't put multiple entry points in front of one backend pool (condition 2) — the trigger in our incident. If you need redundancy, give each LB its own backend pool.
  • Split backend ports or pools (condition 3), so different paths land on different rs_ip:rs_port.
  • Use L7 with backend long connections (condition 1) and read the client IP from X-Forwarded-For.
  • Don't allow direct connections that bypass the load balancer — a direct path plus an LB path is two entry points (condition 2).

How to diagnose it

Crossing looks like unexplained resets, corrupted or interleaved data, or two clients "interfering" with each other. To confirm:

  • Map the full topology. Look specifically for multiple front-end paths converging on one backend IP and port — the signature is a shared backend pool.
  • On the backend, capture traffic and look for two flows presenting the same four-tuple, or connection-table anomalies for a four-tuple that should be unique.
  • Enable L7 access logs if using an HTTP/HTTPS listener, to trace individual requests.

A quick mental check — crossing is possible when:

source-IP pass-through
  AND multiple front-end paths
  AND same backend IP:port
  AND client reuses source IP:port
  AND connections overlap in time

All five true → possible. Any one false → impossible.

Takeaways

  • Source-IP pass-through erases the VIP and port from the four-tuple. That is convenient for logging real client IPs and the root enabler of crossing.
  • Crossing needs five conditions at once. Breaking any single one prevents it — usually the easiest is "don't share one backend pool across multiple entry points."
  • Session persistence does not help. It adds no distinguishing information; it can make collisions more likely.
  • L7 with backend long connections is the clean fix. The proxy's own address occupies the source fields; the client IP moves to X-Forwarded-For.
