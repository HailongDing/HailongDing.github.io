An Unattended Kernel Upgrade That Broke Boot After a Cloud Migration

Posted on May 20, 2024 ()

Categories: linux  cloud  boot 

A customer running Ubuntu 22.04 hit an intermittent, alarming failure: every so often the machine would come up after a reboot into a broken state and drop to an emergency shell. It did not happen on every reboot, and nothing the customer did on purpose seemed to trigger it.

The pattern turned out to be: an automatic kernel upgrade, followed by a reboot, followed by a machine that could not find its root filesystem. And the underlying reason was a piece of configuration that had quietly hitchhiked along when the image was migrated from another cloud.

The symptom

On the failed boots, the serial console showed the kernel loading and then giving up because the disk it was told to mount did not exist:

ALERT!  PARTUUID=895d8984-5441-4c70-b87c-a6b6ebb8c95e does not exist.
Dropping to a shell!

The kernel was looking for a root partition identified by a specific PARTUUID, and no partition on this machine had that UUID. So it could not assemble root, and it bailed out to an initramfs shell.

Tracing the trigger

Three observations lined up:

  • After a failed boot there was a new kernel installed that had not been there before — something was upgrading the kernel without anyone asking.
  • /boot/grub/grub.cfg had been modified — the boot configuration was being regenerated as part of that upgrade.
  • /var/log/apt/history.log showed the change had been made by /usr/bin/unattended-upgrade.

So the chain of events was: Ubuntu's unattended-upgrades — the package that installs security updates automatically — pulled in a new kernel, which regenerated the GRUB configuration, and on the next reboot the machine tried to boot with a root reference it could not satisfy. The upgrade itself was routine and correct; the problem was what it regenerated the config from.

The root cause: a hard-coded UUID from another cloud

This image had been migrated from AWS. On AWS, the image had pinned the root partition to a fixed PARTUUID, via a GRUB drop-in file:

/etc/default/grub.d/40-force-partuuid.cfg

That file forces GRUB to use a specific PARTUUID for the root device. It exists because AWS's environment guarantees that particular UUID — it is tied to how their images and volumes are provisioned. It is an AWS-specific assumption baked into the image.

On the new platform, that guarantee does not hold. Here, a disk's UUID is a property of the actual volume attached to the instance, not something fixed by the image. So the disk on this machine had a different PARTUUID than the one hard-coded in 40-force-partuuid.cfg.

Here is why it was intermittent rather than immediate: the running grub.cfg from the original image may have been fine, or the machine had booted successfully on whatever config it shipped with. The failure only surfaced when unattended-upgrades regenerated grub.cfg — because regeneration re-read 40-force-partuuid.cfg and wrote the stale, hard-coded PARTUUID into the new boot entry. Until an automatic upgrade fired, nothing rewrote the config, so the machine kept booting. That is why it looked random: the trigger was the upgrade schedule, not anything the customer did.

The fix

Recovery, from the emergency shell or a rescue environment:

# find the offending drop-in
$ grep -rl PARTUUID /etc/default/grub.d/
/etc/default/grub.d/40-force-partuuid.cfg

# remove or neutralise the AWS-specific pin
$ sudo rm /etc/default/grub.d/40-force-partuuid.cfg

# regenerate the boot config without the hard-coded UUID
$ sudo update-grub

With the forced-PARTUUID drop-in gone, update-grub generates a boot entry that resolves the root device normally, and the machine boots and stays bootable across future upgrades. Rebooting out of rescue mode confirmed it.

If you would rather keep the pin than remove it — for instance if something else depends on it — the alternative is to correct it: find the disk's actual identifier (blkid /dev/vda1) and update the file to match, rather than the value carried over from AWS.

The broader lesson: images carry hidden assumptions

The interesting part of this case is not the one broken file — it is why it was there. A machine image is not a neutral bag of bits; it encodes assumptions about the environment it was built for. Device naming, UUID stability, network interface names, cloud-init datasource, metadata endpoints, DHCP behaviour — an image built on one platform can hard-code any of these, and they may be silently wrong on another.

What made this one nasty is the delayed detonation. The bad assumption sat dormant through the migration and the first boots, and only fired when an unrelated automated process (a security upgrade) happened to regenerate the file that contained it. Cause and effect were separated by days and by an event nobody connected to the disk.

A few habits that catch this class of problem:

  • After migrating an image between clouds, audit the boot path. Check /etc/default/grub and /etc/default/grub.d/, /etc/fstab, and the initramfs for hard-coded device IDs, and regenerate grub.cfg yourself so you find out immediately rather than at the next automatic upgrade.
  • Prefer stable-but-portable references. Filesystem UUID or label in fstab is generally more portable than a partition-table UUID pinned by a cloud-specific drop-in.
  • Know what unattended-upgrades will do. Automatic security updates are good policy, but on a migrated image they are also the thing most likely to regenerate boot config from stale inputs. Test a kernel upgrade and reboot deliberately after a migration, rather than letting the first one happen unattended in production.

Takeaways

  • PARTUUID ... does not exist at boot means the boot config references a disk identifier that isn't present — very often a value carried over from a different environment.
  • Migrated images carry environment-specific assumptions. A UUID that a previous cloud guaranteed is not guaranteed elsewhere.
  • An unattended upgrade can expose a dormant fault. The bug was latent until something regenerated grub.cfg; that is why it looked intermittent.
  • Audit the boot path right after a cross-cloud migration — GRUB drop-ins, fstab, initramfs — and force a config regeneration and reboot on your own schedule.
