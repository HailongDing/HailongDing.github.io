Out of Inodes, Not Space: A Filesystem Killed by a Mail Loop

Categories: filesystems  linux  troubleshooting 

A customer's cloud VM suddenly refused SSH logins. With their permission we got in through the VNC console, and the moment we tried to do anything that touched disk, the problem announced itself: the filesystem could not be written to. It had gone read-only.

What followed was a satisfying chain — read-only root, plenty of free space but zero free inodes, a directory stuffed with millions of tiny files, and at the bottom of it all a PHP script caught in a loop it did not know it was in.

The serial log: a read-only root

The serial console log showed the root filesystem had been mounted read-only after the kernel detected it needed recovery:

EXT3-fs (vda1): recovery required on readonly filesystem
EXT3-fs (vda1): write access will be enabled during recovery
kjournald starting.  Commit interval 5 seconds
EXT3-fs (vda1): orphan cleanup on readonly fs
EXT3-fs (vda1): 26 orphan inodes deleted
EXT3-fs (vda1): recovery complete
EXT3-fs (vda1): mounted filesystem with ordered data mode

When a filesystem hits an error condition it cannot safely continue through, the kernel's default is to remount it read-only to protect what is there. A read-only root explains everything upstream: SSH could not write session state, login machinery could not create the files it needs, and the box became effectively unusable while still being "up." (The root here was ext3; the data disk, as it turned out, was ext4.)

Space was fine. Inodes were gone.

We booted into rescue mode and mounted the disk under /mnt/vm1 to inspect it without the OS fighting back. df -h looked healthy — plenty of free gigabytes. But df -i told the real story:

$ df -h /mnt/vm1        # space: lots free
$ df -i /mnt/vm1        # inodes: 100% used
Filesystem      Inodes   IUsed  IFree IUse%
/dev/...        ...      ...        0  100%

This is a failure mode that surprises people, so it is worth being precise about the mechanism.

A traditional Linux filesystem like ext3/ext4 allocates its inodes at format time. An inode is the metadata record for a single file or directory — owner, permissions, timestamps, and pointers to the data blocks. The filesystem sets aside a fixed number of them based on the volume size, on the assumption of an "average" file size. Two independent resources can therefore run out:

  • Data blocks — run out and you have "no space left," the familiar case. Reported by df -h.
  • Inodes — run out and you cannot create a single new file even with terabytes of free space, because there is no metadata record left to describe it. Reported by df -i.

Every file, no matter how small — even a zero-byte file — consumes exactly one inode. So a workload that creates enormous numbers of tiny files exhausts inodes long before it exhausts space. The error the application sees is ENOSPC ("No space left on device"), which is thoroughly misleading: there is space; there are just no inodes. Always check df -i when a "disk full" error appears on a disk that clearly is not full.

Finding the offending directory

The next question is where all the files are. Counting files per directory finds the hotspot:

# which directory holds the most files
$ find /mnt/vm1 -xdev -type f | cut -d/ -f1-5 | sort | uniq -c | sort -rn | head

One directory dominated — millions of files. Clearing it immediately restored the inode count to normal, and the filesystem was healthy again.

Except it did not stay healthy. After a reboot and a while running, the same directory filled up again, and the machine failed the same way. Deleting the files treated the symptom; something was actively generating them.

Catching the culprit with atop

Platform-side monitoring gave the first real clue: the guest's process count was climbing continuously, and the failure reproduced right when the process count peaked. So whatever was making the files was also spawning processes without bound — the two were the same runaway.

To catch it in the act we cleared the directory again and deployed atop, which samples process activity at intervals and, crucially, records short-lived processes that a live top would never catch. That surfaced a PHP process churning away.

The loop

Piecing it together, the mechanism was a self-sustaining loop:

  1. The PHP program hit an execution error.
  2. On error, it tried to send an email — a notification about the failure.
  3. The email could not be delivered, so it was queued: a file appeared under /var/spool/postfix/maildrop.
  4. The process then restarted immediately, hit the same error, and sent another undeliverable mail — another file.

Round and round, as fast as the machine allowed. Each iteration left one more file in the mail spool. Given a directory accumulating files at that rate, inode exhaustion was only a matter of time — and because the failure notification was itself failing, the "error handler" had become the error, generating exactly the condition it was meant to warn about.

There is a nasty positive-feedback quality to it: the more it failed, the more mail it tried to send, the more files it created, the closer the filesystem got to the wall that would make everything fail.

The fix

  • Break the loop. The real fix is in the application: do not retry instantly and unconditionally on error, and do not emit an undeliverable email on every failure. Add backoff, a retry cap, and a circuit breaker so a persistent failure does not become an infinite one.
  • Fix mail delivery, or stop queuing. If the mail cannot be delivered, the spool grows forever. Either make delivery work or configure the app not to enqueue mail it cannot send.
  • Drain the spool. Clear the accumulated maildrop files to recover the inodes immediately.
  • Monitor inodes, not just space. Alert on df -i reaching a high-water mark. Inode exhaustion is invisible to the usual "disk usage" alarms, which is why this ran all the way to failure.
  • Cap process count. A per-user process limit (ulimit -u / cgroup pids.max) turns "runaway loop takes down the box" into "runaway loop hits a ceiling and gets noticed."

Takeaways

  • "No space left" on a disk that isn't full means inodes. Check df -i before df -h when the numbers don't add up.
  • ext3/ext4 fix their inode count at format time. Many small files exhaust inodes long before blocks; every file costs one inode regardless of size.
  • A read-only remount is the kernel protecting the filesystem. It explains SSH/login failures on a machine that is otherwise "up."
  • Deleting the files is not the fix if something is creating them. Use atop to catch short-lived processes, and correlate with a climbing process count.
  • A failing error handler is the worst kind. An undeliverable error-notification loop manufactured the exact resource exhaustion it existed to warn about.
