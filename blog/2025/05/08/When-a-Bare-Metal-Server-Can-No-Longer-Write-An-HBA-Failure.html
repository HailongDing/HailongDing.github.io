When a Bare-Metal Server Can No Longer Write: An HBA Failure

Posted on May 8, 2025 ()

Categories: hardware  storage  troubleshooting 

A bare-metal server started refusing writes. Applications that tried to save data failed, the filesystem misbehaved, and the machine was clearly unwell — but it was not obvious why. This one is short, because the value is in the diagnostic path rather than a clever fix: it is a worked example of reading down the stack, from the application's complaint to the piece of hardware actually at fault.

Layer 1: the application log

The starting point was the customer's own application logs inside the OS, which showed write operations failing. That tells you something is wrong, but an application-level write error is the least specific signal there is — it could be a full disk, a read-only filesystem, permissions, a quota, or hardware. An application only knows that a write() came back with an error; it cannot see why.

So the application log is where you start, never where you stop. The job is to keep descending until the layers stop pointing further down.

Layer 2: system messages

Next was /var/log/messages, which sits below the application and records what the operating system itself noticed. Here the errors were more specific — the kernel was logging I/O problems, not just an application unhappy about a failed save. That confirmed the fault was below the application layer: this was the storage stack failing, not a bug in the customer's code or a full volume.

Layer 3: the kernel ring buffer

Then dmesg, the kernel's ring buffer, which carries the lowest-level messages the kernel emits — including what device drivers report. This is where the trail ended, because the driver errors named the culprit directly: the messages pointed at the HBA (Host Bus Adapter) — the card that connects the server to its storage.

The HBA had failed. With the adapter faulting, I/O to the disks behind it could not complete, which the kernel surfaced as I/O errors in messages, which the application experienced as writes that would not go through. Every symptom up the stack was a faithful echo of one hardware failure at the bottom.

Why the top-down order matters

It is tempting, once you suspect hardware, to jump straight to dmesg. The reason to walk the layers in order anyway is that each one tells you whether to keep going and in which direction:

  • Application log — that something is wrong, and roughly what operation. (Writes failing.)
  • System log (messages) — whether the OS itself sees a problem. If the OS is happy, look back up at the application; if the OS reports I/O errors, keep going down. (It reported I/O errors.)
  • Kernel buffer (dmesg) — the raw driver- and device-level truth, where a failing controller announces itself. (HBA errors.)

Walking it in order also stops you misattributing the cause. A read-only filesystem, for instance, produces very similar application-level symptoms but has a completely different signature in messages and dmesg. Letting each layer either implicate or exonerate the one below keeps you from fixing the wrong thing.

What an HBA is, and why its failure is total

The HBA is the interface card between the server and its storage — SAS/SATA drives or a storage fabric. Everything the machine reads or writes to those disks passes through it. When it fails, it does not usually degrade gracefully; it takes down access to everything behind it at once. That is why the symptom was systemic — not one bad file or one bad disk, but writes failing broadly — and why the fix is replacement, not repair. On a bare-metal machine that means swapping the physical card (or migrating the workload to healthy hardware); there is no software remedy for a dead adapter.

This is also a reminder of what "bare metal" costs you. On a virtual machine, this class of hardware failure is the provider's problem — the hypervisor abstracts the storage adapter away and a failing host triggers a migration underneath you. On bare metal you get the performance and isolation of dedicated hardware, and in exchange you own the physical fault domain: a failed HBA is now visible to you and yours to resolve.

Takeaways

  • Diagnose top-down: application log → messages → dmesg. Each layer tells you whether the fault is above or below it, and points you at the next place to look.
  • An application write error is a symptom, not a diagnosis. The app only knows the write failed; the cause lives further down.
  • dmesg is where hardware confesses. Driver and device errors — like a failing HBA — surface here when higher layers only show generic I/O failures.
  • An HBA failure is systemic. It affects all storage behind the adapter at once, and the fix is replacement — a cost that is yours to bear on bare metal but the provider's on a VM.
