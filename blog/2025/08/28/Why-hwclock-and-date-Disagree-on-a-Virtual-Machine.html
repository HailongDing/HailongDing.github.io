Why hwclock and date Disagree on a Virtual Machine

Categories: virtualization  timekeeping  linux 

A customer noticed something that looked like a bug: on their cloud VM, hwclock and date reported different times. The system clock said one thing, the hardware clock said another, and the gap between them was not zero.

Testing across a range of instance types and operating systems turned up a genuinely interesting pattern, and it leads to the same practical advice as a related timekeeping problem I wrote about earlier: in a virtual machine, do not trust the hardware clock. This post looks at the discrepancy from the other direction — not "why won't my RTC change stick," but "why do the two clocks disagree at all, and why does the gap grow?"

Two clocks, and why they differ

A Linux system has two distinct notions of time:

  • The system clock (what date shows) — maintained by the kernel in memory, advanced by a high-resolution timer, and, if you run a time daemon, disciplined against a network source. This is the time everything actually uses.
  • The hardware clock or RTC (what hwclock shows) — on a physical machine, a battery-backed chip that keeps time while the power is off. Its main job is to seed the system clock at boot before the network is up.

On a healthy physical machine these track each other closely because the RTC is a real, stable oscillator and the OS periodically writes the system time back to it. On a VM, the relationship is much weaker — and that is the crux.

The pattern: more vCPUs, bigger gap

The revealing finding from testing across many machine types was this: the more virtual CPUs an instance had, the larger the difference between hwclock and date tended to be. The discrepancy was not random noise; it scaled with the size of the instance.

That correlation is the clue to the whole thing. It points away from "the RTC is broken" and toward the cost of reading a simulated clock in a virtual environment — a cost that grows with how much virtual hardware the hypervisor has to coordinate.

Why a virtual hardware clock drifts

In a VM there is no battery-backed chip. The "hardware clock" is emulated by the hypervisor, and that changes its behaviour in ways that produce exactly this symptom:

  • The guest doesn't run continuously. The hypervisor schedules the VM against other work on the host; from inside, time effectively pauses whenever the guest is descheduled. On a bigger instance there is more to coordinate — more vCPUs to schedule, more contention — so the reading of an emulated clock is more affected.
  • Reads are not instantaneous or perfectly synchronised. Reading an emulated device involves the hypervisor. Across many vCPUs, those reads are not all perfectly aligned, and small inconsistencies accumulate into a visible offset.
  • Lifecycle events cause jumps. Live migration to another host, resume from suspend, or heavy host load all perturb the guest's sense of time — sometimes by large amounts. The underlying timestamp counter can differ between hosts, so a migration produces a discontinuity.

So the emulated RTC is inherently a less reliable timekeeper than a physical one, and its unreliability is more pronounced precisely on the larger, busier instances — which is the correlation the testing found.

The fix: ignore the hardware clock, run NTP

The recommendation is the same one every cloud vendor's documentation gives, and it is the correct resolution here: do not rely on the hardware clock in a VM. Synchronise the system clock over the network with NTP.

  • Run a time daemon — chrony is the modern default and handles virtualised environments well. Point it at your platform's NTP endpoint. The system clock (date) is then continuously disciplined against an accurate external source and stays correct regardless of what the emulated RTC is doing.
  • Stop treating hwclock as authoritative. Its purpose — seeding time across a power-off — barely applies to a VM, which gets its time from the host and the network anyway. A disagreement between hwclock and date on a VM is expected, not a fault to chase.
  • Expect and allow for jumps. Virtualisation lifecycle events can cause large time jumps, and by default ntpd will give up if it sees a jump beyond a sanity threshold — on the reasonable assumption that such a leap indicates a fault. In a VM that leap is routine, so configure the daemon to keep correcting: tinker panic 0 for ntpd, or the equivalent makestep handling that chrony does natively.

The underlying mechanics, briefly

For the curious, the reason this is hard is timestamp counters. Physical timekeeping leans on the CPU's TSC, whose frequency is measured once at boot. Virtualisation breaks the assumptions: after a live migration the new host's TSC differs, so the value "jumps," and the frequency measured at boot is no longer the true frequency. Hypervisors paper over this with paravirtualised clocks — pvclock for Xen and KVM guests, the TSC reference page for Hyper-V — fixed-frequency sources the host keeps meaningful across migration, from which the guest computes the real time. Modern guests use these automatically, which is why the situation is far better than it once was. But the emulated RTC specifically remains a weak timekeeper, which is why the guidance is to bypass it in favour of NTP.

Takeaways

  • hwclock ≠ date on a VM is normal. They are two different clocks, and the hardware one is emulated.
  • The gap scaling with vCPU count is the tell. It points at the cost of coordinating an emulated clock across more virtual hardware, not at a broken RTC.
  • A VM's emulated hardware clock is not a reliable time source. Migration, suspend/resume, and host load all perturb it.
  • Run NTP against the system clock, and let the daemon keep correcting through jumps. chrony handles this well; with ntpd, set tinker panic 0.
