The Password That Reset Itself Every Morning

Categories: security  linux  troubleshooting 

A customer had a genuinely strange complaint. Every morning, a little after 10 o'clock, their server would stop accepting the login password. Resetting the password fixed it — until the next day, when the same password would again be mysteriously changed and they were locked out once more.

A password that changes itself, on a schedule, is unsettling. It sounds like a compromise, and that is exactly what the customer feared. It turned out to be the opposite — but proving that required a technique worth writing up in its own right: tracing which program is invoking a command, when the logs won't tell you.

The logs said nothing

The obvious first move was to read the logs around 10 a.m. — the system message log and the authentication log. They showed the password change happening, but nothing useful about who or what was doing it. There was no login session to blame, no obvious command in anyone's shell history, no cron job with an obvious name. The change was happening, and the standard audit trail did not name a culprit.

This is the frustrating middle of many investigations: you know what is happening and roughly when, but not which process is responsible. You need to catch the actor in the act.

The technique: wrap the command to trace its caller

When a command keeps running and you cannot tell what is invoking it, one effective (if blunt) technique is to replace the command with a wrapper that records who called it and then passes through to the real command. The wrapper walks up the process tree at the moment of invocation and logs the entire call chain — so instead of "the password was changed," you get "process X, launched by Y, launched by Z, changed the password."

The mechanism is simple and relies only on the /proc filesystem. For any process ID you can read:

  • /proc/<pid>/cmdline — the exact command line it was invoked with;
  • /proc/<pid>/stat — among other things, its parent PID.

Starting from the wrapper's own PID and following the parent PID upward until you reach PID 1, you reconstruct the full ancestry of whatever triggered the command. A compact script captures it:

#!/usr/bin/perl
# trace_call.pl — log the full call chain, then exec the real command.
use strict; use warnings;
use Cwd qw(getcwd); use POSIX qw(strftime);

my $orig_dir  = "/usr/local/orig_bin";   # where the real binary was moved
my $trace_log = "/var/log/trace_call.log";

sub cmdline { my $p=shift; open my $f,"<","/proc/$p/cmdline" or return [];
    local $/; my @c=split /\0/, scalar <$f>; \@c }
sub ppid    { my $p=shift; open my $f,"<","/proc/$p/stat" or return 1;
    local $/; (split /\s+/, scalar <$f>)[3] }

# build the ancestry chain up to PID 1
my @chain; my $pid=$$;
while ($pid > 1) { unshift @chain, [$pid, cmdline($pid)]; $pid = ppid($pid); }

open my $log, ">>", $trace_log;
print {$log} "="x60, "\n", strftime("%F %T",localtime()), "  cwd=", getcwd(), "\n";
print {$log} "  $_->[0]: @{$_->[1]}\n" for @chain;
close $log;

# hand off to the real command, arguments intact
my $self = (split m{/}, $0)[-1];
exec "$orig_dir/$self", @ARGV;

Deploying it is three steps: move the real binary somewhere safe, drop the wrapper in its place, make it executable.

$ mkdir -p /usr/local/orig_bin
$ cp -a /usr/bin/passwd /usr/local/orig_bin/    # preserve the real command
$ cp trace_call.pl /usr/bin/passwd && chmod +x /usr/bin/passwd

From then on, every invocation appends the full caller chain to the log and then runs the genuine command, so behaviour is unchanged while you watch.

Why a wrapper, rather than proper auditing?

The clean way to answer "who ran this command" is the kernel audit subsystem (auditd with a watch on the binary, or an execve audit rule). If audit is available, use it — it is designed for exactly this and does not involve tampering with system binaries.

The wrapper technique earns its place when audit is not available or not enabled — for example on older systems where the kernel was not built with audit support. In that situation, replacing the binary is a pragmatic fallback that needs nothing from the kernel. The idea and this script long predate the investigation here; it is an old sysadmin trick, and it is still the thing you reach for when the tidy option is off the table.

It comes with real caveats, and they are worth stating plainly:

  • It is intrusive. You are modifying a system binary. A host security agent may (rightly) flag the change to a sensitive command.
  • Clean up afterwards. If you forget to restore the original, you leave a permanent wrapper in place that will keep writing logs and could grow a huge file — a mess for whoever finds it later.
  • Be careful which commands you wrap. Wrapping something invoked constantly can generate enormous logs and add overhead.

Use it deliberately, on a specific command, for a bounded window, and undo it when you have your answer.

What the trace revealed

With the wrapper in place, the next morning's 10 a.m. event was captured in full. The call chain named the actor: an automated fleet-management assistant — a platform agent — was resetting the password on schedule.

Not an attacker. Once we knew what to ask, the explanation was quick to confirm: the server was a development box, and the security team's automated tooling had detected that it was using a weak password. To prevent the machine from being compromised through that weak credential, the tooling was automatically resetting the password — every day, because every day the customer set it back to the same weak value.

The "attack" was a defence mechanism, and the customer and the security automation were quietly fighting each other: one restoring a weak password, the other dutifully clearing it. The fix was trivial once understood — the customer set a strong password, the weak-credential detector had nothing to act on, and the daily reset never happened again.

Takeaways

  • "The password changes itself on a schedule" is scary but not necessarily malicious. Automated security tooling can be the thing modifying your system — confirm before assuming compromise.
  • When logs show what but not who, trace the caller. Walking the /proc parent-PID chain reconstructs the full ancestry of a command.
  • Prefer auditd; fall back to a wrapper. Replacing a binary to log its callers works when kernel audit isn't available — but it's intrusive, so scope it tightly and always restore the original.
  • Weak credentials invite automated intervention. On managed platforms, a weak password may be reset for you; set a strong one and the conflict disappears.
