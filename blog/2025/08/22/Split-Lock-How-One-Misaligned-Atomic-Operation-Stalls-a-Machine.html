Split-Lock: How One Misaligned Atomic Operation Stalls a Machine

Posted on August 22, 2025 ()

Categories: hardware  performance  linux kernel 

A customer reported packet loss on their cloud VM — elevated PPS drops, and business-level latency jitter to go with it. The network graphs showed the symptom clearly enough, but the cause was not in the network at all. It was in the CPU, and it has a name worth knowing: split-lock.

This post is less about the specific incident and more about the mechanism, because split-lock is one of those low-level phenomena that produces high-level symptoms — latency, jitter, packet loss — that look like they must be a networking or scheduling problem. Once you know it exists, you recognise the fingerprint.

The symptom

During the affected windows, the customer's own monitoring showed jitter — throughput and latency wobbling rather than holding steady. The platform-side metrics for the same moments confirmed packet drops. Two views, same conclusion: the machine was periodically failing to keep up, in short bursts, and dropping packets when it did.

Bursty, periodic stalls are the tell. A steady overload looks like a flat ceiling; split-lock looks like brief, sharp hitches — the machine freezes for a moment, catches up, freezes again.

What a split-lock is

To understand split-lock you need two ideas: atomic operations and cache lines.

Modern CPUs guarantee that certain memory operations are atomic — they complete indivisibly, so two cores cannot interleave and corrupt a shared value. Atomics are the foundation of locks, counters, and reference counts; they are everywhere in concurrent code.

Memory is moved between RAM and the CPU in fixed-size chunks called cache lines — 64 bytes on x86. Normally the CPU makes an atomic operation atomic cheaply, by locking just the relevant cache line while it works (a "cache lock"). Fast, contained, invisible.

The trouble comes when the data an atomic operation touches is split across two adjacent cache lines — the value straddles the 64-byte boundary. Now the cheap trick does not work: you cannot lock a single cache line, because the data lives in two. To preserve atomicity the CPU falls back to a much heavier hammer — it locks the entire memory bus (a bus lock) for the duration of the operation.

That bus lock is the split-lock. And locking the bus is not a local event.

Why one operation hurts the whole machine

A cache lock affects one cache line. A bus lock affects every core on the socket. While the bus is locked, all other memory traffic stalls — every other core wanting to touch memory has to wait for the split-lock to finish.

So a single misaligned atomic on one thread imposes a pause on the entire machine. One operation, and everyone stops. A single split-lock can cost on the order of thousands of cycles — orders of magnitude more than a normal atomic — and if a program does this in a hot loop, the machine spends a meaningful fraction of its time frozen mid-stride.

That directly explains the customer's symptoms. Packet processing is timing-sensitive and runs on the same cores as everything else. When the bus locks, packet handling stalls along with everything else; buffers back up; and when they overflow, packets drop. The "network problem" was a CPU stall wearing a network costume.

How does the data get misaligned?

Split-locks come from atomic operations on data that is not naturally aligned. In practice that traces back to things like:

  • Packed structures — code that disables the compiler's natural alignment (for wire formats or to save memory) can place a multi-byte field across a cache-line boundary, and then perform an atomic on it.
  • Hand-written or generated assembly that assumes alignment it does not enforce.
  • Manual memory management that hands out buffers without honouring alignment for fields later used atomically.

It is almost always a subtle bug in a specific program, not a system misconfiguration. The program works correctly — the atomic still is atomic — it just achieves that correctness in the most expensive way the hardware offers, and everyone else on the socket pays for it.

Detecting it

The good news is that modern kernels can detect split-locks directly, using a CPU feature (bus-lock / split-lock detection) that traps the event. The kernel documentation covers the interface in full — see Bus lock detection and handling — but the essentials:

  • The kernel can be configured to warn when a split-lock occurs, logging the offending process. This is how you turn an invisible whole-machine stall into a named culprit.
  • It can also be configured to rate-limit offenders (throttling a process that triggers them repeatedly) or to kill them outright, depending on the split_lock_detect policy.
  • Watch dmesg for split-lock / bus-lock warnings once detection is enabled — the log names the process, which points you straight at the code to fix.

Once you have the offending process, the real fix is in that code: align the data so the atomic stays within a single cache line. Alignment is a property of the program, so the durable remedy is a code change; the kernel's rate-limiting is a way to contain the blast radius in the meantime.

Takeaways

  • Split-lock symptoms masquerade as networking or scheduling problems. Bursty packet loss and latency jitter can be a CPU stall, not a network fault.
  • An atomic straddling two cache lines forces a bus lock. The CPU can't lock a single line, so it locks the whole bus.
  • A bus lock stalls every core on the socket. One misaligned atomic on one thread pauses the entire machine — thousands of cycles per event.
  • The root cause is misaligned data, usually from packed structs or manual memory layout. The program is correct but pathologically expensive.
  • Modern kernels can detect and name offenders. Enable split-lock detection, watch dmesg, then fix the alignment in the offending code.
